# 从真实工作到公开记录

来源为天一的 Build in Public 方法论。用真实项目的一次工作切片，交付可以核对的过程和发现。

1. 选一件已经发生的事。读任务记录、产物、前后版本、测试输出或实际反馈。把完成、尝试过、还未做以及无法确认的内容写清。
2. 选一个能讲明白的问题：一个带证据的失败、一个反直觉发现，或自己的系统怎样运行。提取一个具体动作、一个摩擦点、一份结果证据。若涉及数字，注明样本范围和计算口径。若证据只有一条观察，把结论限制在这一条。
3. 写四行骨架：正在做哪件事；遇到什么具体问题；做了什么、结果怎样；读者能复用什么。第四行必须能从前三行推出。缺证据时先保留为观察，写出下一次怎么补。
4. 交付草稿、事实出处和待确认的公开范围。有原话、客户资料或截图时，确认授权与可公开程度。保留足够过程让读者理解适用条件。对外发布由用户明确决定。
5. 发布后有真实反馈时，记下读者追问、可复做反馈或纠错，更新原有工作记录。已有写作样本时可接 voice-anchor 做成文。

虚构示例：三次稿件交接都有遗漏。先列出遗漏发生的节点和影响，然后展示加入一张交接单之后的一次结果。结尾只写「下一单我会继续检查素材来源是否齐全」。三次遗漏和一次试跑不能推导出整个团队效率翻倍。
